## 🏛️ ESCENARIO 1: El Escudo Financiero (SEQUENTIAL_STRICT)

* **La Crisis Real:** En un flujo de pagos, usted descuenta saldo (Paso 1), pero el sistema de compensación cae (Paso 2). Si el orquestador sigue ejecutando a ciegas, abonará el dinero a la cuenta destino (Paso 3) sin haberlo descontado correctamente, causando un descuadre financiero.
* **Para qué sirve este modo:** `SEQUENTIAL_STRICT` garantiza que las tareas se ejecuten en orden estricto (1, 2, 3...) y **actúa como un escudo (Tolerancia Cero)**: si un paso falla, la guillotina cae y el resto de la cadena jamás se ejecuta.

**Ejecución:**

```sql
SELECT bg.launch_job_one_shot(
    '01_PAGO_NOMINA_CRITICO', 
    'SEQUENTIAL_STRICT', 
    ARRAY[
        'INSERT INTO bg_lab.evidencia_procesos (escenario, mensaje) VALUES (''CASO_01'', ''Paso 1: Saldo descontado exitosamente.'');',
        'SELECT 1 / 0; -- ERROR SIMULADO: Caída de la red de compensación.',
        'INSERT INTO bg_lab.evidencia_procesos (escenario, mensaje) VALUES (''CASO_01'', ''Paso 3: Transferencia realizada (¡ESTO SERÍA UN FRAUDE SI SE EJECUTA!)'');'
    ],
    p_timeout_seconds => 10,
    p_max_retries => 0
);

```

**🔍 Cómo Validarlo (Auditoría):**

1. **Valide el Tablero:** `SELECT * FROM bg.vw_status_progreso_corporativo WHERE "Nombre del Job" = '01_PAGO_NOMINA_CRITICO';`
*(Verá el Estatus Real como `❌ FALLIDO CON ERRORES` clavado al 33% de avance).*
2. **Valide la Evidencia Física:** `SELECT * FROM bg_lab.evidencia_procesos WHERE escenario = 'CASO_01';`
*(Verá SOLAMENTE el Paso 1. La herramienta salvó a la empresa de ejecutar el Paso 3).*

## 🧹 ESCENARIO 2: Continuidad Operativa (SEQUENTIAL_NORMAL)

* **La Crisis Real:** Son las 3:00 AM. Se debe hacer mantenimiento (VACUUM) a 50 tablas. La tabla número 2 fue borrada por accidente ayer. Si el sistema es "Estricto", el mantenimiento se abortará y 48 tablas amanecerán lentas.
* **Para qué sirve este modo:** `SEQUENTIAL_NORMAL` asimila el error. Registra la falla de la tarea 2 en la bitácora, la aísla, y **obliga al servidor a continuar** con las tareas 3 a la 50 para garantizar la operatividad de la empresa.

**Ejecución:**

```sql
SELECT bg.launch_job_one_shot(
    '02_MANTENIMIENTO_NOCTURNO', 
    'SEQUENTIAL_NORMAL', 
    ARRAY[
        'INSERT INTO bg_lab.evidencia_procesos (escenario, mensaje) VALUES (''CASO_02'', ''Optimizando Tabla Ventas'');',
        'SELECT * FROM tabla_fantasma; -- ERROR SIMULADO',
        'INSERT INTO bg_lab.evidencia_procesos (escenario, mensaje) VALUES (''CASO_02'', ''Optimizando Tabla Clientes (El motor sobrevivió al error)'');'
    ],
    p_timeout_seconds => 10,
    p_max_retries => 0
);

```

**🔍 Cómo Validarlo (Auditoría):**

1. **Valide el Tablero:** Revise el Tablero y verá `✅ FINALIZADO` pero con `Hechas: 2, Errores: 1`. ¡Transparencia total!
2. **Valide la Evidencia:** `SELECT * FROM bg_lab.evidencia_procesos WHERE escenario = 'CASO_02';` *(Verá que las tablas 1 y 3 sí se procesaron).*

## ⚡ ESCENARIO 3: Ráfaga de Fin de Mes (PARALLEL_INITIAL)

* **La Crisis Real:** En el cierre de mes, se deben emitir estados de cuenta masivos. Ejecutarlos uno por uno toma horas, desesperando a la gerencia.
* **Para qué sirve este modo:** Lanza **todas las tareas al mismo tiempo**, forzando al hardware (CPU) a trabajar en paralelo. Lo que tomaría 20 segundos secuenciales, se resuelve en 4 segundos de reloj.

**Ejecución (4 tareas pesadas simultáneas):**

```sql
SELECT bg.launch_job_one_shot(
    '03_CIERRE_CONTABLE_MASIVO', 
    'PARALLEL_INITIAL', 
    ARRAY[
        'SELECT pg_sleep(4);', 'SELECT pg_sleep(4);', 'SELECT pg_sleep(4);', 'SELECT pg_sleep(4);'
    ]
);

```

**🔍 Cómo Validarlo (Auditoría Visual en Vivo):**

* Ejecute este query repetidamente durante 4 segundos:
`SELECT "Workers Activos (Motor)", "Duración", "Estatus Real" FROM bg.vw_status_progreso_corporativo WHERE "Nombre del Job" = '03_CIERRE_CONTABLE_MASIVO';`
*(Verá a 4 Workers devorando el trabajo al mismo tiempo. Al llegar a los 4 segundos, el Job terminará).*

## 🚦 ESCENARIO 4: El Administrador de Tráfico (RANDOM + Límites)

* **La Crisis Real:** Un desarrollador junior lanza 1,000 conexiones pesadas (ETL) al mismo tiempo contra la base de datos de Producción, provocando que el servidor se quede sin RAM (Out Of Memory) y colapse todo el corporativo.
* **Para qué sirve este modo:** Usted define una "válvula de seguridad" (`max_parallel_processes`). El motor Orquestador encolará las 1,000 tareas, pero **solo dejará pasar de N en N**, inyectando una nueva únicamente cuando se libere un espacio.

**Ejecución (Lanzamos 5 tareas, pero limitamos la válvula a 2):**

```sql
SELECT bg.launch_job_one_shot(
    '04_CARGA_ETL_CUELLO_BOTELLA', 
    'RANDOM', 
    ARRAY[
        'SELECT pg_sleep(3);', 'SELECT pg_sleep(3);', 'SELECT pg_sleep(3);', 'SELECT pg_sleep(3);', 'SELECT pg_sleep(3);'
    ],
    p_max_parallel_processes => 2 -- LA VÁLVULA DE SEGURIDAD
);

```

**🔍 Cómo Validarlo (Auditoría del Embudo):**

* Monitoree el tablero cada segundo:
*(Notará que "Workers Activos" jamás supera el número 2. La columna "En Espera" irá bajando de 3 a 0 de forma rítmica sin colapsar el servidor).*

## 🔪 ESCENARIO 5: El Verdugo Inquebrantable (Timeouts y Reintentos)

* **La Crisis Real:** Una consulta a una tabla remota (dblink) se queda "colgada" por un fallo en el módem, reteniendo bloqueos vitales y paralizando las ventas por horas hasta que un DBA la mata manualmente.
* **Para qué sirve este modo:** El Padre Orquestador vigila con cronómetro en mano. Si una tarea excede su tiempo de vida, **el Padre la asesina a nivel de Sistema Operativo (`pg_cancel_backend`)** y, si usted lo indica, la reintenta para descartar micro-cortes.

**Ejecución:**

```sql
SELECT bg.launch_job_one_shot(
    '05_PRUEBA_RESILIENCIA_EXTREMA', 
    'SEQUENTIAL_NORMAL', 
    ARRAY[
        'WITH RECURSIVE t(n) AS (VALUES (1) UNION ALL SELECT n+1 FROM t) SELECT count(*) FROM t; -- Bucle infinito devora-CPU'
    ],
    p_timeout_seconds => 2, -- Si tarda más de 2s, MATAR
    p_max_retries => 0      -- Sin piedad, cero reintentos
);

```

**🔍 Cómo Validarlo (Auditoría Forense):**

* Espere 3 segundos y pregúntele a la base de datos cómo murió la tarea:
```sql
SELECT run_id, status, error_log FROM bg.run_tasks ORDER BY run_id DESC LIMIT 1;

```


*(La bitácora dirá contundentemente `FAILED` y la razón de muerte será: "Aniquilado por el Padre (Timeout estricto)". Usted no tuvo que intervenir; el framework protegió el servidor).*

## 📜 ESCENARIO 6: Inmutabilidad Histórica (El Caso Juan y Roberto)

* **La Crisis Real:** Juan crea un Job. Roberto lo ejecuta en enero. En febrero, Juan actualiza el Job y le borra 2 pasos. Al consultar los reportes de enero, la base de datos truena por errores de "Llaves Foráneas" o muestra datos históricos falseados (modificados por el cambio de febrero).
* **Para qué sirve este modo:** El framework usa **Snapshots Desacoplados**. Cada ejecución es una fotografía congelada en el tiempo. Usted puede reescribir y alterar las plantillas (`def_jobs`) 100 veces, y las bitácoras históricas jamás se corromperán.

**Ejecución:**

```sql
-- 1. Se define la plantilla (Día 1)
SELECT bg.create_job_definition('06_CIERRE_CAJA', 'SEQUENTIAL_NORMAL', ARRAY['SELECT pg_sleep(1);']);

-- 2. Se lanza el Job (Queda en el historial con 1 tarea)
SELECT bg.launch_job_by_name('06_CIERRE_CAJA');

-- 3. Se RE-ESCRIBE la plantilla atómicamente agregando más carga (Día 2)
SELECT bg.create_job_definition('06_CIERRE_CAJA', 'SEQUENTIAL_NORMAL', ARRAY['SELECT pg_sleep(1);', 'SELECT pg_sleep(1);', 'SELECT pg_sleep(1);']);

-- 4. Se lanza la nueva versión
SELECT bg.launch_job_by_name('06_CIERRE_CAJA');

```

**🔍 Cómo Validarlo (Auditoría):**

* Revise el tablero filtrando por ese nombre. Verá dos registros con el mismo nombre de Job, pero uno indica `Total Tareas: 3` y debajo de él en la historia, el registro viejo intacto marca `Total Tareas: 1`.

## 💥 ESCENARIO 7 (NUEVO): Ráfagas de Estrés con `replicate_query`

* **La Crisis Real:** El equipo de QA necesita simular 500 inicios de sesión simultáneos o 500 inserciones pesadas para probar la infraestructura. Pegar 500 líneas en un array de texto colapsa el editor SQL, es poco profesional y propenso a errores humanos.
* **Para qué sirve este comando:** El multiplicador atómico reserva espacio en la RAM (O(1)) y clona su consulta instantáneamente el número de veces que usted ordene.

**Ejecución (Simulemos 100 inserciones concurrentes en 1 sola línea de código):**

```sql
SELECT bg.launch_job_one_shot(
    '07_ESTRES_DE_SISTEMA_MASIVO', 
    'PARALLEL_INITIAL', -- Disparo a quemarropa simultáneo
    
    -- La Magia: Clonamos 100 veces el INSERT
    bg.replicate_query(
        'INSERT INTO bg_lab.evidencia_procesos (escenario, mensaje) VALUES (''CASO_07'', ''Transacción de Estrés Masivo procesada.'');', 
        100
    ),
    
    p_timeout_seconds => 60,
    p_max_retries => 0
);

```

**🔍 Cómo Validarlo (Auditoría de Ingesta Masiva):**

1. Vaya al tablero y verá un Job con `Total Tareas: 100`, procesándose a velocidades de microsegundos.
2. Compruebe la efectividad real en disco:
```sql
SELECT COUNT(*) AS total_inserciones FROM bg_lab.evidencia_procesos WHERE escenario = 'CASO_07';

```


*(El contador devolverá exactamente **100**. Usted generó una prueba de carga masiva escribiendo menos de 10 líneas de código).*
