## 🏛️ ESCENARIO 1: El Flujo Financiero (Secuencial Estricto)

* **El Caso de Uso:** Imagine un flujo de transferencia bancaria o facturación. Paso 1: Descontar saldo. Paso 2: Registrar impuestos. Paso 3: Abonar a la cuenta destino. Si el Paso 2 falla (ej. error de red o de cálculo), **el Paso 3 jamás debe ejecutarse** para evitar regalar dinero o corromper el balance.
* **El Objetivo:** Comprobar la "Tolerancia Cero". El motor debe detectar la falla en la cadena y abortar todo el Job instantáneamente.

**Ejecute el Disparo:**

```sql
SELECT resilient_bg.launch_job_one_shot(
    '01_TRANSFERENCIA_BANCARIA', 
    'SEQUENTIAL_STRICT', 
    ARRAY[
        'INSERT INTO resilient_bg_lab.evidencia_procesos (caso_uso, mensaje) VALUES (''CASO_01'', ''Paso 1: Saldo descontado con éxito'');',
        'SELECT 1 / 0; -- SIMULAMOS CAÍDA DEL SISTEMA DE IMPUESTOS',
        'INSERT INTO resilient_bg_lab.evidencia_procesos (caso_uso, mensaje) VALUES (''CASO_01'', ''Paso 3: Abono realizado (¡PELIGRO SI ESTO SE EJECUTA!)'');'
    ],
    p_timeout_seconds => 15,
    p_max_retries => 0
);

```

**🔍 Cómo Revisar (Auditoría):**

1. Verifique el Tablero: `SELECT * FROM resilient_bg.vw_status_progreso_corporativo WHERE "Nombre del Job" = '01_TRANSFERENCIA_BANCARIA';`
*(Notará que el Estatus Real es `❌ FALLIDO CON ERRORES` y se detuvo en 33%).*
2. Verifique la tabla de evidencias: `SELECT * FROM resilient_bg_lab.evidencia_procesos WHERE caso_uso = 'CASO_01';`
*(Observará únicamente el Paso 1. El motor actuó como escudo y evitó el Paso 3).*

## 🧹 ESCENARIO 2: Mantenimiento Nocturno (Secuencial Normal)

* **El Caso de Uso:** Procesos rutinarios como optimización de tablas (`VACUUM`, `ANALYZE`), regeneración de índices o envío de correos. Si una tabla no existe o un correo falla, el sistema debe reportarlo, pero **tiene la obligación de continuar** con el resto de la lista para que la empresa amanezca operando.
* **El Objetivo:** Comprobar la "Resiliencia de Continuidad". El motor anota el error, lo asimila, y sigue adelante.

**Ejecute el Disparo:**

```sql
SELECT resilient_bg.launch_job_one_shot(
    '02_MANTENIMIENTO_NOCTURNO', 
    'SEQUENTIAL_NORMAL', 
    ARRAY[
        'INSERT INTO resilient_bg_lab.evidencia_procesos (caso_uso, mensaje) VALUES (''CASO_02'', ''Tabla Clientes Optimizada'');',
        'SELECT * FROM tabla_que_no_existe; -- ERROR INDUCIDO',
        'INSERT INTO resilient_bg_lab.evidencia_procesos (caso_uso, mensaje) VALUES (''CASO_02'', ''Tabla Inventarios Optimizada (Continuó exitosamente)'');'
    ],
    p_timeout_seconds => 15,
    p_max_retries => 0
);

```

**🔍 Cómo Revisar (Auditoría):**

1. Tabla de evidencias: `SELECT * FROM resilient_bg_lab.evidencia_procesos WHERE caso_uso = 'CASO_02';`
*(Verá ambas tablas optimizadas, el Job no se rindió).*
2. Tablero Analítico: Revisará que el Job terminó (`✅ FINALIZADO`) pero le advertirá de forma transparente: `Hechas: 2`, `Errores: 1`.

## ⚡ ESCENARIO 3: Ráfaga de Fin de Mes (Paralelo Inicial)

* **El Caso de Uso:** Es el cierre de mes. Necesita generar 5 reportes financieros masivos e independientes. Si los corre secuencialmente, el servidor tardará 20 minutos (4 minutos por reporte). Si los lanza en paralelo, el motor usará 5 núcleos del servidor y tardará solo 4 minutos totales.
* **El Objetivo:** Acelerar tiempos de respuesta inyectando carga distribuida al procesador.

**Ejecute el Disparo:**

```sql
-- Simulamos 4 reportes que tardan 4 segundos exactos en procesarse cada uno.
SELECT resilient_bg.launch_job_one_shot(
    '03_CIERRE_FINANCIERO_MASIVO', 
    'PARALLEL_INITIAL', 
    ARRAY[
        'SELECT pg_sleep(4);',
        'SELECT pg_sleep(4);',
        'SELECT pg_sleep(4);',
        'SELECT pg_sleep(4);'
    ]
);

```

**🔍 Cómo Revisar (Auditoría Visual):**

* **Velocidad:** Ejecute rápidamente la consulta al Tablero `vw_status_progreso_corporativo`.
* **Resultados:** Verá `"Workers Activos (Motor)" = 4`. Tras pasar los 4 segundos, el Job se marcará como finalizado. Logramos 16 segundos de trabajo de hardware condensados en solo 4 segundos netos de reloj.

## 🚦 ESCENARIO 4: El Administrador de Tráfico (Random + Límites)

* **El Caso de Uso:** Tenemos una cola gigantesca de 5 procesos pesados (ej. procesamiento de nómina), pero sabemos que si lanzamos los 5 al mismo tiempo (como en el escenario anterior), la memoria RAM del servidor colapsará. Necesitamos limitar la ejecución a **máximo 2 a la vez**.
* **El Objetivo:** Comprobar el sistema *Zero-Lock* de gestión de colas. El orquestador debe ser lo suficientemente inteligente para inyectar tareas nuevas únicamente cuando un canal se desocupa.

**Ejecute el Disparo:**

```sql
SELECT resilient_bg.launch_job_one_shot(
    '04_PROCESAMIENTO_CONTROLADO', 
    'RANDOM', 
    ARRAY[
        'SELECT pg_sleep(5);',
        'SELECT pg_sleep(5);',
        'SELECT pg_sleep(5);',
        'SELECT pg_sleep(5);',
        'SELECT pg_sleep(5);'
    ],
    p_max_parallel_processes => 2 -- LÍMITE CORPORATIVO DE CANALES
);

```

**🔍 Cómo Revisar (Auditoría Constante):**

* Monitorice el tablero durante 15 segundos: `SELECT * FROM resilient_bg.vw_status_progreso_corporativo WHERE "Nombre del Job" = '04_PROCESAMIENTO_CONTROLADO';`
* **Magia de Concurrencia:** Verá que `"Workers Activos"` jamás superará el número 2. La columna `"En Espera"` irá bajando de 3 a 2, a 1, fluyendo como un embudo perfecto hasta llegar al 100%.

## 🛡️ ESCENARIO 5: El Sicario de Timeouts y la Segunda Oportunidad

* **El Caso de Uso:** Uno de sus procesos intenta conectarse a un servicio externo o ejecutar una consulta mal indexada que se queda "colgada" para siempre (bloqueando el sistema). Queremos que el sistema mate ese proceso si tarda más de 2 segundos, pero que, por si fue un parpadeo de red, le dé una segunda oportunidad (1 reintento).
* **El Objetivo:** Validar el sistema de aniquilación de conexiones (`pg_cancel_backend`) y el re-encolado automático.

**Ejecute el Disparo:**

```sql
SELECT resilient_bg.launch_job_one_shot(
    '05_PRUEBA_RESILIENCIA', 
    'SEQUENTIAL_NORMAL', 
    ARRAY[
        'SELECT pg_sleep(10); -- Este proceso intentará durar 10 segundos'
    ],
    p_timeout_seconds => 2, -- Límite de muerte: 2 segundos
    p_max_retries => 1      -- Política de resiliencia: 1 intento extra
);

```

**🔍 Cómo Revisar (Auditoría Forense):**

1. Espere aproximadamente 6 segundos y consulte el histórico interno del sistema:

```sql
SELECT rj.run_id, rt.attempt, rt.status, rt.error_log 
FROM resilient_bg.run_tasks rt
JOIN resilient_bg.run_jobs rj ON rt.run_id = rj.run_id
JOIN resilient_bg.def_jobs dj ON rj.job_id = dj.job_id
WHERE dj.job_name = '05_PRUEBA_RESILIENCIA';

```

* **Resultados:** Comprobará que la tabla de tareas registra `attempt: 2`. Verá en el `error_log` el mensaje exacto donde el proceso Padre asesinó al proceso colgado: *"Timeout excedido"*.

## 🏭 ESCENARIO 6: Flujo Operativo Corporativo (El Turno de Juan y Roberto)

* **El Caso de Uso:** En el corporativo, los DBA o Arquitectos (Juan) preparan las rutinas de cierre en la mañana. Los operadores nocturnos (Roberto) no saben de SQL, solo llegan y le dan "Play" al proceso por su nombre.
* **El Objetivo:** Comprobar que la base de datos se mantiene limpia (idempotencia) y que la separación de plantillas y bitácoras históricas V6 es a prueba de balas.

**Paso 6.1 (Turno Matutino): Juan crea la rutina.**

```sql
SELECT resilient_bg.create_job_definition(
    '06_CIERRE_OPERATIVO',
    'SEQUENTIAL_NORMAL',
    ARRAY[
        'INSERT INTO resilient_bg_lab.evidencia_procesos (caso_uso, mensaje) VALUES (''CASO_06'', ''Paso 1: OK'');',
        'INSERT INTO resilient_bg_lab.evidencia_procesos (caso_uso, mensaje) VALUES (''CASO_06'', ''Paso 2: OK'');'
    ]
);

```

**Paso 6.2 (Turno Nocturno): Roberto lanza el proceso sin tocar código.**

```sql
SELECT resilient_bg.launch_job_by_name('06_CIERRE_OPERATIVO') AS corrida_lunes;

```

**Paso 6.3 (Siguiente Día): Juan cambia las reglas (Actualiza el Job).**

```sql
-- Juan añade un paso extra a la rutina. (En la versión vieja, esto fallaba por llave foránea).
SELECT resilient_bg.create_job_definition(
    '06_CIERRE_OPERATIVO',
    'SEQUENTIAL_NORMAL',
    ARRAY[
        'INSERT INTO resilient_bg_lab.evidencia_procesos (caso_uso, mensaje) VALUES (''CASO_06'', ''Paso 1: OK'');',
        'INSERT INTO resilient_bg_lab.evidencia_procesos (caso_uso, mensaje) VALUES (''CASO_06'', ''Paso 2: OK'');',
        'INSERT INTO resilient_bg_lab.evidencia_procesos (caso_uso, mensaje) VALUES (''CASO_06'', ''Paso 3: NUEVO PASO AGREGADO HOY'');'
    ]
);

```

**Paso 6.4: Roberto lanza la nueva versión el Martes.**

```sql
SELECT resilient_bg.launch_job_by_name('06_CIERRE_OPERATIVO') AS corrida_martes;

```

**🔍 Cómo Revisar (Auditoría de Inmutabilidad):**

```sql
SELECT "ID Ejecución", "Nombre del Job", "Total Tareas", "Hechas", "Estatus Real" 
FROM resilient_bg.vw_status_progreso_corporativo 
WHERE "Nombre del Job" = '06_CIERRE_OPERATIVO'
ORDER BY "ID Ejecución" DESC;

```

* **Resultado Exquisito:** Verá la corrida del Martes con `Total Tareas = 3`. Y justo debajo, verá la corrida del Lunes intacta y protegida en el tiempo con `Total Tareas = 2`. Cero errores de llaves foráneas, separación histórica perfecta.
