## 🏛️ ESCENARIO 1: El Escudo Financiero (Secuencial Estricto)

* **Caso de Uso:** Actualización de saldos. Paso 1: Bloquear cuenta. Paso 2: Transferir fondos. Paso 3: Desbloquear. Si la transferencia falla, el proceso debe abortarse instantáneamente para que intervenga auditoría.
* **Objetivo:** Validar que el motor *Zero-Lock* respeta la tolerancia cero y corta la cadena de ejecución al primer error.

**Ejecución:**

```sql
SELECT resilient_bg.launch_job_one_shot(
    '01_TRANSFERENCIA_CRITICA', 
    'SEQUENTIAL_STRICT', 
    ARRAY[
        'INSERT INTO resilient_bg_lab.evidencia_procesos (escenario, mensaje) VALUES (''CASO_01'', ''Paso 1: Cuenta Bloqueada'');',
        'SELECT 1 / 0; -- FALLO CRÍTICO DE RED SIMULADO',
        'INSERT INTO resilient_bg_lab.evidencia_procesos (escenario, mensaje) VALUES (''CASO_01'', ''Paso 3: Transferencia (¡PELIGRO SI SE VE ESTO!)'');'
    ],
    p_timeout_seconds => 15,
    p_max_retries => 0
);

```

**🔍 Cómo Auditar:**

1. **Vista Gerencial:** `SELECT * FROM resilient_bg.vw_status_progreso_corporativo WHERE "Nombre del Job" = '01_TRANSFERENCIA_CRITICA';`
*Verá el estatus `❌ FALLIDO CON ERRORES`, `Hechas: 1`, `Errores: 1`, `Avance: 33%`.*
2. **Evidencia Física:** `SELECT * FROM resilient_bg_lab.evidencia_procesos WHERE escenario = 'CASO_01';`
*Verá únicamente el "Paso 1". La base de datos fue protegida.*

## 🛡️ ESCENARIO 5: El Aniquilador y el Reintento (Resiliencia Extrema)

* **Caso de Uso:** Una conexión a un servidor remoto se queda colgada (latencia infinita). Queremos que el motor la mate a los 2 segundos, y automáticamente intente lanzarla de nuevo por si solo fue un micro-corte.
* **Objetivo:** Probar el `statement_timeout` dinámico introducido en la V7.

**Ejecución:**

```sql
SELECT resilient_bg.launch_job_one_shot(
    '05_PRUEBA_TIMEOUT', 
    'SEQUENTIAL_NORMAL', 
    ARRAY[
        'SELECT pg_sleep(10); -- Sentencia rebelde'
    ],
    p_timeout_seconds => 2, -- Límite de vida: 2 segundos
    p_max_retries => 1      -- Se reintentará 1 vez más
);

```

**🔍 Cómo Auditar:**

1. Espere 6 segundos y consulte la tabla forense del sistema:

```sql
SELECT rt.run_id, rt.attempt, rt.status, rt.error_log 
FROM resilient_bg.run_tasks rt JOIN resilient_bg.run_jobs rj ON rt.run_id = rj.run_id JOIN resilient_bg.def_jobs dj ON rj.job_id = dj.job_id
WHERE dj.job_name = '05_PRUEBA_TIMEOUT';

```

*Verá que el intento (attempt) llega a 2. El `error_log` dirá "canceling statement due to statement timeout", demostrando que el orquestador aniquiló el proceso colgado exitosamente.*
