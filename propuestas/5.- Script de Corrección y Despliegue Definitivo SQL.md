**Sofía (Directora de Calidad y Producto):** Equipo, detengamos todo inmediatamente. El cliente tiene toda la razón en estar molesto: ver un estatus permanente de `⏳ STALE / DESCONECTADO` en un proyecto de misión crítica es inaceptable. Asumimos la responsabilidad absoluta como mesa técnica. Ningún software de alto prestigio se entrega con fallas en la verificación de hechos. Mateo, Elena, Alejandro: saquen la telemetría de los logs del cliente ahora mismo, expongan el motivo exacto del fallo y entreguen la corrección de inmediato.

**Mateo (Especialista en Concurrencia):** Sofía, acabo de detectar el problema en la telemetría del motor (`pg_stat_activity`). Es un comportamiento fascinante de la concurrencia de PostgreSQL, pero catastrófico para el script anterior. El log muestra exactamente esto:

* El proceso Padre (`bg_job_orchestrator`) está atrapado en un evento de espera de tipo `Timeout / PgSleep`.
* El proceso Hijo (`bg_task_executor`) está congelado esperando un evento de tipo `Lock / transactionid`.

**Elena (DBA Expert):** ¡Claro! Qué miopía técnica tuvimos. Diseñamos el orquestador como una `FUNCTION` de PL/pgSQL. En Postgres, **las funciones son atómicas y se ejecutan dentro de una única transacción indivisible**. Cuando el Padre ejecutaba el `UPDATE` para guardar el `child_pid` del hijo, *bloqueaba la fila de la tarea*. Al ser una función, ese bloqueo no se liberaba hasta que la función terminara. Acto seguido, el Hijo despertaba en su propio worker e intentaba hacer un `UPDATE` a la misma fila para ponerse en estado `RUNNING`. ¿El resultado? **Un bloqueo mutuo infinito (Deadlock de sesión)**. El Padre esperaba que el Hijo cambiara de estado, y el Hijo esperaba que el Padre liberara el bloqueo de la transacción. Por eso la vista siempre mostró `STALE`, porque la transacción del Padre nunca se guardaba (*uncommitted*) y hacia afuera el sistema seguía pareciendo `INITIALIZING`.

**Alejandro (Líder de Desarrollo):** Entendido por completo. Para resolver este cuello de botella arquitectónico, debemos migrar el Orquestador de una `FUNCTION` a un **`PROCEDURE` (Procedimiento Almacenado)** corporativo. Los procedimientos en PostgreSQL admiten el control autónomo de transacciones mediante la instrucción **`COMMIT;`**. Al introducir un `COMMIT` inmediatamente después de lanzar cada proceso hijo, liberamos los bloqueos de las filas al instante, permitiendo que la información fluya en tiempo real al motor y que la vista analítica muestre el progreso de forma impecable.

Además, detecté dos errores operacionales humanos en las pruebas del cliente:

1. **Error de Base de Datos:** Tras reiniciar el servidor, el cliente ejecutó comandos en la base de datos por defecto (`postgres`) en lugar de reconectarse a la base de datos del negocio (`bk`), lo que arrojó el error de que el esquema no existía.
2. **Error de ID Hardcodeado (Caso Juan/Roberto):** El script generó el Job con el ID `6`, pero el cliente intentó ejecutar el ID `12` siguiendo literalmente el ejemplo genérico del manual. Para solucionar esto y elevar el nivel comercial, añadiré una función helper para lanzar Jobs directamente por su **Nombre Corporativo**, eliminando la necesidad de adivinar IDs numéricos.

## 🛠️ Script de Corrección y Despliegue Definitivo (.SQL)

Ejecute este script en la base de datos del negocio (`bk`). Este elimina las funciones restrictivas y migra la arquitectura a Procedimientos de alta disponibilidad con liberación atómica de bloqueos.

```sql
-- ============================================================================
-- FRAMEWORK CORPORATIVO DE ORQUESTACIÓN ASÍNCRONA RESILIENTE (FOAR) V2
-- COMPONENTE: Script de Corrección y Parche de Concurrencia Crítica
-- ============================================================================

BEGIN;

-- 1. Eliminar la función vieja que causaba el bloqueo mutuo
DROP FUNCTION IF EXISTS resilient_bg.bg_job_orchestrator(INT);

COMMIT;

-- 2. RECONSTRUCCIÓN: El Orquestador ahora es un PROCEDIMIENTO ALMACENADO con control de transacciones
CREATE OR REPLACE PROCEDURE resilient_bg.bg_job_orchestrator(p_run_id INT)
AS $$
/**
  OBJETIVO: Supervisor maestro (Padre). Orquesta las colas utilizando COMMITs intermedios
            para liberar bloqueos de filas y permitir la concurrencia real sin deadlocks.
*/
DECLARE
    v_job_id INT;
    v_mode resilient_bg.execution_mode;
    v_timeout INT;
    v_max_retries INT;
    v_max_parallel INT;
    
    v_run_task_id INT;
    v_child_pid INT;
    v_active_slots INT;
    v_current_status resilient_bg.task_status;
    v_task_duration INTERVAL;
    v_curr_attempt INT;
    v_final_errors INT;
BEGIN
    -- Registrar PID del Monitor y confirmar transacción inmediatamente para que sea visible externamente
    UPDATE resilient_bg.run_jobs 
    SET monitor_pid = pg_backend_pid(), status = 'RUNNING', started_at = CURRENT_TIMESTAMP 
    WHERE run_id = p_run_id;
    COMMIT; 

    -- Extraer parámetros operacionales
    SELECT dj.job_id, dj.mode, dj.timeout_seconds, dj.max_retries, dj.max_parallel_processes
    INTO v_job_id, v_mode, v_timeout, v_max_retries, v_max_parallel
    FROM resilient_bg.run_jobs rj
    JOIN resilient_bg.def_jobs dj ON rj.job_id = dj.job_id
    WHERE rj.run_id = p_run_id;

    IF v_mode = 'PARALLEL_INITIAL' THEN
        SELECT COUNT(*) INTO v_max_parallel FROM resilient_bg.run_tasks WHERE run_id = p_run_id;
    END IF;

    -- ========================================================================
    -- MODOS SECUENCIALES (STRICT / NORMAL)
    -- ========================================================================
    IF v_mode IN ('SEQUENTIAL_STRICT', 'SEQUENTIAL_NORMAL') THEN
        
        -- Usamos un bucle WHILE controlado para evitar mantener cursores abiertos entre COMMITs
        WHILE EXISTS (SELECT 1 FROM resilient_bg.run_tasks WHERE run_id = p_run_id AND status = 'PENDING') LOOP
            
            SELECT rt.run_task_id INTO v_run_task_id
            FROM resilient_bg.run_tasks rt
            JOIN resilient_bg.def_tasks dt ON rt.task_id = dt.task_id
            WHERE rt.run_id = p_run_id AND rt.status = 'PENDING'
            ORDER BY dt.execution_order ASC
            LIMIT 1;

            WHILE TRUE LOOP
                -- Lanzar el proceso Hijo de manera asíncrona
                SELECT pg_background_launch(format('SELECT resilient_bg.bg_task_executor(%L)', v_run_task_id)) 
                INTO v_child_pid;
                
                -- Guardar traza inicial del Hijo y hacer COMMIT para liberar la fila instantáneamente
                UPDATE resilient_bg.run_tasks SET child_pid = v_child_pid WHERE run_task_id = v_run_task_id;
                COMMIT; 

                -- Bucle de espera pasiva del Padre
                WHILE TRUE LOOP
                    COMMIT; -- REFRESH DE SNAPSHOT: Permite leer los cambios guardados por el Hijo
                    PERFORM pg_sleep(0.1); 
                    
                    SELECT status, (CURRENT_TIMESTAMP - started_at) INTO v_current_status, v_task_duration
                    FROM resilient_bg.run_tasks WHERE run_task_id = v_run_task_id;

                    -- Control de Timeout
                    IF v_current_status = 'RUNNING' AND EXTRACT(EPOCH FROM v_task_duration) > v_timeout THEN
                        PERFORM pg_cancel_backend(v_child_pid);
                        UPDATE resilient_bg.run_tasks SET status = 'KILLED', error_log = 'Timeout alcanzado.' WHERE run_task_id = v_run_task_id;
                        COMMIT;
                        v_current_status := 'KILLED';
                    END IF;

                    IF v_current_status IN ('SUCCESS', 'FAILED', 'KILLED') THEN
                        EXIT;
                    END IF;
                END LOOP;

                -- Gestión de éxito o reintentos
                IF v_current_status = 'SUCCESS' THEN
                    EXIT; 
                ELSE
                    SELECT attempt INTO v_curr_attempt FROM resilient_bg.run_tasks WHERE run_task_id = v_run_task_id;
                    
                    IF v_curr_attempt <= v_max_retries THEN
                        UPDATE resilient_bg.run_tasks SET attempt = v_curr_attempt + 1, status = 'PENDING' WHERE run_task_id = v_run_task_id;
                        COMMIT;
                    ELSE
                        IF v_mode = 'SEQUENTIAL_STRICT' THEN
                            UPDATE resilient_bg.run_jobs SET status = 'FAILED', ended_at = CURRENT_TIMESTAMP WHERE run_id = p_run_id;
                            COMMIT;
                            RETURN;
                        END IF;
                        EXIT; 
                    END IF;
                END IF;
            END LOOP;
        END LOOP;

    -- ========================================================================
    -- MODOS CONCURRENTES (PARALLEL / RANDOM)
    -- ========================================================================
    ELSE
        WHILE EXISTS (SELECT 1 FROM resilient_bg.run_tasks WHERE run_id = p_run_id AND status IN ('PENDING', 'RUNNING')) LOOP
            COMMIT; -- Actualizar contexto transaccional

            -- 1. Monitoreo de Timeouts
            FOR v_run_task_id IN (SELECT run_task_id FROM resilient_bg.run_tasks WHERE run_id = p_run_id AND status = 'RUNNING') LOOP
                SELECT child_pid, (CURRENT_TIMESTAMP - started_at) INTO v_child_pid, v_task_duration
                FROM resilient_bg.run_tasks WHERE run_task_id = v_run_task_id;

                IF EXTRACT(EPOCH FROM v_task_duration) > v_timeout THEN
                    PERFORM pg_cancel_backend(v_child_pid);
                    UPDATE resilient_bg.run_tasks SET status = 'KILLED', error_log = 'Timeout concurrente.' WHERE run_task_id = v_run_task_id;
                    COMMIT;
                END IF;
            END LOOP;

            -- 2. Procesamiento de Reintentos
            FOR v_run_task_id IN (SELECT run_task_id FROM resilient_bg.run_tasks WHERE run_id = p_run_id AND status IN ('FAILED', 'KILLED')) LOOP
                SELECT attempt INTO v_curr_attempt FROM resilient_bg.run_tasks WHERE run_task_id = v_run_task_id;
                IF v_curr_attempt <= v_max_retries THEN
                    UPDATE resilient_bg.run_tasks SET attempt = v_curr_attempt + 1, status = 'PENDING' WHERE run_task_id = v_run_task_id;
                    COMMIT;
                END IF;
            END LOOP;

            -- 3. Despacho de canales (Slots)
            SELECT COUNT(*) INTO v_active_slots FROM resilient_bg.run_tasks WHERE run_id = p_run_id AND status = 'RUNNING';

            IF v_active_slots < v_max_parallel THEN
                SELECT run_task_id INTO v_run_task_id FROM resilient_bg.run_tasks WHERE run_id = p_run_id AND status = 'PENDING' LIMIT 1;

                IF v_run_task_id IS NOT NULL THEN
                    UPDATE resilient_bg.run_tasks SET status = 'RUNNING', started_at = CURRENT_TIMESTAMP WHERE run_task_id = v_run_task_id;
                    COMMIT; -- Confirmar estado RUNNING antes de lanzar para evitar condiciones de carrera

                    SELECT pg_background_launch(format('SELECT resilient_bg.bg_task_executor(%L)', v_run_task_id)) INTO v_child_pid;
                    
                    UPDATE resilient_bg.run_tasks SET child_pid = v_child_pid WHERE run_task_id = v_run_task_id;
                    COMMIT; 
                END IF;
            END IF;

            PERFORM pg_sleep(0.1);
        END LOOP;
    END IF;

    -- Auditoría de finalización del Job Completo
    SELECT COUNT(*) INTO v_final_errors FROM resilient_bg.run_tasks WHERE run_id = p_run_id AND status IN ('FAILED', 'KILLED');
    
    IF v_final_errors > 0 THEN
        UPDATE resilient_bg.run_jobs SET status = 'FAILED', ended_at = CURRENT_TIMESTAMP WHERE run_id = p_run_id;
    ELSE
        UPDATE resilient_bg.run_jobs SET status = 'COMPLETED', ended_at = CURRENT_TIMESTAMP WHERE run_id = p_run_id;
    END IF;
    COMMIT;
END;
$$ LANGUAGE plpgsql;

-- 3. AJUSTE DE LA API PÚBLICA: Modificar start_job para invocar el PROCEDIMIENTO usando CALL
CREATE OR REPLACE FUNCTION resilient_bg.start_job(p_job_id INT)
RETURNS INT AS $$
DECLARE
    v_run_id INT;
BEGIN
    INSERT INTO resilient_bg.run_jobs (job_id, status)
    VALUES (p_job_id, 'INITIALIZING')
    RETURNING run_id INTO v_run_id;

    INSERT INTO resilient_bg.run_tasks (run_id, task_id, status)
    SELECT v_run_id, task_id, 'PENDING'
    FROM resilient_bg.def_tasks
    WHERE job_id = p_job_id;

    -- Modificado de SELECT a CALL debido a la migración a PROCEDIMIENTO
    PERFORM pg_background_launch(format('CALL resilient_bg.bg_job_orchestrator(%L)', v_run_id));
    
    RETURN v_run_id;
END;
$$ LANGUAGE plpgsql;

-- 4. VALOR AGREGADO: Helper Premium para lanzar Jobs por NOMBRE (Evita errores de ID del cliente)
CREATE OR REPLACE FUNCTION resilient_bg.launch_job_by_name(p_job_name VARCHAR(100))
RETURNS INT AS $$
DECLARE
    v_job_id INT;
BEGIN
    SELECT job_id INTO v_job_id FROM resilient_bg.def_jobs WHERE job_name = p_job_name;
    
    IF v_job_id IS NULL THEN
        RAISE EXCEPTION 'Error de Operaciones: El Job con nombre "%" no existe registrado.', p_job_name;
    END IF;
    
    RETURN resilient_bg.start_job(v_job_id);
END;
$$ LANGUAGE plpgsql;

```
